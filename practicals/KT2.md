# КТ 2. Практические работы — 25 баллов

## Перед началом

Вы продолжаете работать с учебным приложением для отправки и просмотра заявок. Здесь **стенд** — это приложение и всё, что нужно для его работы, запущенное на вашем компьютере.

У приложения две части:

- **`web`** — часть, через которую пользователь работает с приложением в браузере.
- **`api`** — часть, к которой `web` обращается для работы с заявками. API — это способ, которым одна программа передаёт запросы другой и получает ответы.

Когда вы отправляете заявку через страницу, одной работающей страницы недостаточно: `web` должен связаться с `api`. Поэтому в работах вы будете проверять и отдельные части приложения, и их совместную работу.

**Docker Compose** позволяет описать части приложения и их настройки в одном файле, а затем управлять ими командами. В этом файле части приложения называются **сервисами**. Например, сервис `web` задаёт, из какого образа и с какими настройками запускать контейнер веб-части.

Выполняйте все команды из **корневой папки своей копии проекта** — основной папки, в которой находится `compose.yaml`, если в задании не указано «внутри контейнера».

Для КТ 2–4 понадобятся результаты предыдущих этапов. Сохраняйте созданные файлы и выполненные настройки.

В заданиях вы будете использовать собственный файл `compose.student.yaml`. Чтобы Docker Compose использовал именно его, указывайте `-f compose.student.yaml`. Это тот же проект с теми же томами для хранения данных, а не отдельный стенд.

## Как оформлять сдачу

Для каждой работы сдайте изменённые файлы проекта и отдельный отчёт `evidence/K2-XX.md`, где `XX` — номер работы. `evidence` — папка с подтверждениями выполнения, а `.md` — текстовый файл в формате Markdown.

В отчёте укажите команды, свои наблюдения и вывод. Наблюдение — что вы действительно увидели: ответ приложения, сообщение об ошибке, состояние контейнера. Вывод — что этот результат показывает и почему он получился.

Общие правила сдачи также предусматривают ссылки на прогоны для CI — автоматических проверок проекта — и JSON-файл для панели. Это относится к работам, где есть такие задания; отдельно делать их для этих пяти работ не требуется. Для устной работы или работы со схемой достаточно схемы и ответа в отчёте.

## K2-01. Образ и контейнер — 4 балла

**Что здесь происходит.** Образ — подготовленный набор файлов и настроек, из которого Docker создаёт контейнеры. Контейнер — отдельный экземпляр приложения со своим состоянием. Из одного образа можно создать несколько контейнеров: общая основа у них одна, но работать они могут независимо и выполнять разные роли.

В этой работе вы рассматриваете уже запущенный стенд. Затем останавливаете только его веб-часть и наблюдаете, что меняется для пользователя.

**Задача:** найти образ и два созданных из него контейнера, остановить и снова запустить `web`, затем повторить отправку заявки.

1. На работающем стенде выполните:

    ```bash
    docker image inspect devops-course:base
    docker compose ps
    ```

    `docker image inspect` показывает сведения об образе, а `docker compose ps` — контейнеры проекта и их состояние. Это два разных вида информации: о том, из чего запускают приложение, и о созданных экземплярах приложения.

2. Найдите образ `devops-course:base` и два контейнера, созданных на его основе. Определите, какую роль выполняет каждый контейнер.
3. Остановите только сервис `web`:

    ```bash
    docker compose stop web
    ```

4. Попробуйте открыть страницу приложения. Убедитесь, что она недоступна.
5. Снова запустите `web`:

    ```bash
    docker compose start web
    ```

6. Откройте страницу и попробуйте отправить заявку.

**Что сдать:** отчёт `evidence/K2-01.md`. Укажите выполненные команды, результаты проверки и вывод: как остановка `web` повлияла на приложение. Если меняли файлы проекта, включите изменения в сдаваемую работу.

**За что начисляются баллы:**

- Найдены и описаны свойства образа — 1 балл.
- Найдены два контейнера и объяснены их роли — 1 балл.
- Выполнены остановка и повторный запуск `web` — 1 балл.
- Подтверждена отправка заявки после запуска и объяснён результат — 1 балл.

**Вопрос для защиты:** удаляется ли образ, когда вы останавливаете `web`?

## K2-02. Свой Dockerfile — 7 баллов

**Что здесь происходит.** Раньше вы использовали готовый образ. Теперь подготовите собственный с помощью **Dockerfile** — текстового файла с инструкциями для сборки. Docker прочитает этот файл и создаст образ; отдельной командой вы запустите из него контейнер.

`templates/Dockerfile.example` — шаблон, на который нужно ориентироваться. `bootstrap` — название разобранного в курсе образца для первоначального запуска. Используйте его, чтобы понять устройство Dockerfile.

В Dockerfile `COPY` задаёт, какие файлы попадут в образ, `CMD` — какую команду выполнять при запуске контейнера, а `USER` — от имени какого пользователя будет работать приложение. Права на `/data` определяют, сможет ли этот пользователь записывать данные в указанную папку внутри контейнера. `LABEL` добавляет к образу информационную метку: в этой работе по ней можно определить автора.

**Задача:** написать Dockerfile, собрать свой образ и запустить из него контейнер.

1. Создайте файл `lab/Dockerfile`, ориентируясь на `templates/Dockerfile.example`. Используйте разобранный пример `bootstrap` как подсказку.
2. Добавьте в Dockerfile метку `LABEL course.student` со своим кодом студента.
3. Соберите образ:

    ```bash
    docker build -f lab/Dockerfile -t devops-student:v1 lab
    ```

    В команде сборки `-f lab/Dockerfile` указывает файл с инструкциями, `-t devops-student:v1` задаёт имя образа и его тег `v1`. Последнее `lab` — папка с файлами, доступными при сборке. Сборка образа ещё не означает запуск приложения.

4. Проверьте свою метку в сведениях об образе (`docker image inspect`) — это предусмотрено критериями работы.
5. Запустите контейнер:

    ```bash
    docker run --rm -d --name student-web -p 127.0.0.1:8081:8000 -e ROLE=web devops-student:v1
    ```

    Эта команда запускает образ `devops-student:v1` как контейнер с именем `student-web`. Параметр `-d` оставляет его работать в фоне, а `-e ROLE=web` передаёт приложению настройку: выполнять роль `web`. Параметр `--rm` означает, что после остановки этот контейнер будет автоматически удалён.

    `127.0.0.1:8081:8000` связывает порт `8081` вашего компьютера с портом `8000` внутри контейнера. Порт — номер, по которому обращаются к конкретной программе на компьютере или в контейнере. Здесь доступ разрешён через адрес вашего компьютера `127.0.0.1`, также известный как `localhost`.

6. Откройте `http://localhost:8081/health` и проверьте ответ приложения.

    `/health` — адрес проверки состояния приложения. Ответ на него помогает проверить, что запущенная веб-часть отвечает на запросы. Он сам по себе не подтверждает, что весь процесс отправки заявки работает.

    В этом отдельном запуске нет API: вы запустили только `student-web`. Приём заявок проверяется в следующей работе.

7. Посмотрите логи контейнера — сообщения, которые приложение записывает во время работы, — и остановите его:

    ```bash
    docker logs student-web
    docker stop student-web
    ```

**Что сдать:** созданный `lab/Dockerfile` и отчёт `evidence/K2-02.md`. В отчёте укажите команды, результаты сборки и запуска, найденную метку и ответ `/health`. Объясните назначение инструкции Dockerfile, как указано в критериях работы.

**За что начисляются баллы:**

- Правильно использованы `COPY` и `CMD` — 1 балл.
- Настроены `USER` и права доступа к `/data` — 1 балл.
- Образ успешно собран — 1 балл.
- Своя метка найдена в выводе `docker image inspect` — 1 балл.
- Контейнер запущен — 1 балл.
- Получен ответ `/health` — 1 балл.
- Объяснено назначение инструкции Dockerfile — 1 балл.

**Вопрос для защиты:** почему указания `EXPOSE` в Dockerfile недостаточно, чтобы открыть приложение через браузер? Для чего нужен параметр `-p`?

## K2-03. Compose и сохранность данных — 7 баллов

**Что здесь происходит.** В предыдущей работе вы запустили отдельно веб-часть. Теперь ваш образ будет использоваться для двух сервисов — `web` и `api`, — чтобы приложение снова работало целиком. Их роли и остальные настройки уже описаны в Compose-файле.

`API_URL` — настройка, которая сообщает веб-части, по какому адресу обращаться к API. Внутри сети Compose сервисы могут обращаться друг к другу по именам, например `api`. Адрес для связи между контейнерами и адрес, который вы открываете в браузере на своём компьютере, — разные точки доступа.

Кроме связи между сервисами, вы проверите хранение данных. **Том** — отдельное хранилище, которое подключается к контейнеру. **Пересоздать контейнер** означает заменить его новым, а не просто остановить и запустить прежний. Проверка старой заявки покажет, сохраняются ли данные при такой замене.

**Задача:** запустить приложение на своём образе и проверить, сохраняются ли заявки после пересоздания контейнера.

1. Скопируйте `compose.yaml` в `compose.student.yaml`.
2. В настройках сервисов `api` и `web` замените значение `image` на `devops-student:v1`. Остальные сервисы пока не меняйте.
3. Остановите исходный стенд:

    ```bash
    docker compose stop
    ```

4. Дальше в этой работе используйте только `compose.student.yaml`. Проверьте настройки и запустите приложение:

    ```bash
    docker compose -f compose.student.yaml config
    docker compose -f compose.student.yaml up -d
    ```

    `config` проверяет, может ли Compose прочитать настройки, и показывает итоговую конфигурацию. Это ещё не проверка работающего приложения. `up -d` создаёт или обновляет нужные контейнеры и запускает их в фоне.

5. Создайте заявку через приложение и запишите её номер.
6. Пересоздайте контейнер `api`:

    ```bash
    docker compose -f compose.student.yaml up -d --no-deps --force-recreate api
    ```

    `--force-recreate` требует создать контейнер заново, даже если его настройки не изменились. `--no-deps` ограничивает запуск выбранным сервисом, не запуская его зависимости. Здесь выбран сервис `api`.

7. Дождитесь готовности API. Проверьте, что ранее созданная заявка сохранилась, затем создайте ещё одну.

**Что сдать:** файл `compose.student.yaml` и отчёт `evidence/K2-03.md`. Укажите команды, номер первой заявки и результаты проверки после пересоздания контейнера. Объясните назначение `API_URL`, связь между сервисами, используемые порты и том для хранения данных. Добавьте краткую инструкцию запуска.

**За что начисляются баллы:**

- Сервисы `api` и `web` работают на вашем образе — 1 балл.
- Объяснены `API_URL` и связь сервисов через внутреннюю сеть — 1 балл.
- Объяснено назначение используемых портов — 1 балл.
- Объяснено назначение тома для хранения данных — 1 балл.
- Новая заявка успешно создана — 1 балл.
- Старая заявка сохранилась после пересоздания контейнера — 1 балл.
- Есть понятная инструкция запуска — 1 балл.

## K2-04. Registry — 4 балла

**Что здесь происходит.** До этого ваш образ хранился в Docker на вашем компьютере. **Registry** — хранилище, в которое отправляют образы, чтобы затем получать их по адресу и имени. В этой работе само хранилище тоже запускается локально, поэтому регистрироваться на внешнем сайте не нужно.

В имени `localhost:5000/workshop:v1` часть `localhost:5000` — адрес хранилища, `workshop` — имя образа в нём, а `v1` — **тег**, удобная именованная отметка версии. Тег можно назначить другому содержимому. **Digest** — идентификатор, вычисляемый по содержимому; он позволяет точно указать, какой вариант был отправлен или получен.

**Задача:** отправить свой образ в локальное хранилище образов — registry — и скачать его обратно.

1. Запустите локальный registry:

    ```bash
    docker compose --profile registry up -d registry
    ```

    Профиль `registry` включает дополнительную часть настроек Compose, а последнее `registry` в команде — сервис, который нужно запустить.

2. Добавьте образу тег с адресом этого хранилища:

    ```bash
    docker tag devops-student:v1 localhost:5000/workshop:v1
    ```

3. Отправьте образ в registry:

    ```bash
    docker push localhost:5000/workshop:v1
    ```

4. Скачайте образ из registry:

    ```bash
    docker pull localhost:5000/workshop:v1
    ```

    `tag` добавляет образу ещё одно имя, `push` передаёт образ в хранилище, а `pull` получает его оттуда. Если нужные данные уже есть локально, Docker может использовать их повторно: отсутствие повторного скачивания всех слоёв само по себе не означает ошибку.

5. Сохраните значение `digest` из вывода `push` или `pull`.
6. Посмотрите сведения о скачанном образе:

    ```bash
    docker image inspect localhost:5000/workshop:v1
    ```

Для работы с локальным registry не нужен аккаунт. Если возникнет сетевая ошибка, покажите её преподавателю. Не отключайте защиту системы.

**Что сдать:** отчёт `evidence/K2-04.md` с командами, результатами отправки и скачивания образа, сохранённым `digest` и объяснением разницы между `tag` и `digest`. Если меняли файлы проекта, приложите изменения.

**За что начисляются баллы:**

- Образу добавлен тег с адресом registry — 1 балл.
- Образ отправлен командой `push` — 1 балл.
- Образ скачан командой `pull` — 1 балл.
- Сохранён `digest` и объяснена разница между `tag` и `digest` — 1 балл.

**Вопрос для защиты:** почему после `docker push` приложение не запускается автоматически?

## K2-05. Ошибка конфигурации — 3 балла

**Что здесь происходит.** Запущенный контейнер ещё не гарантирует, что приложение выполняет свою задачу. Например, веб-часть может работать, но обращаться к API по неправильному адресу. Тогда пользователь не сможет получить список заявок, хотя сам контейнер `web` не обязательно остановится.

Вы временно измените только номер порта в адресе API. Затем сопоставите два наблюдения: что видит пользователь и что сообщает приложение в логах. После восстановления настройки снова проверите работу через страницу приложения.

**Задача:** намеренно допустить ошибку в настройках, найти её проявление и восстановить работу приложения.

1. Откройте `compose.student.yaml`. В настройках `web` временно замените значение `API_URL` на `http://api:9999`.
2. Примените изменение:

    ```bash
    docker compose -f compose.student.yaml up -d web
    ```

    `up -d web` применяет настройки сервиса `web`; при необходимости Compose пересоздаёт его контейнер. Одного сохранения файла недостаточно, чтобы уже работающая веб-часть получила новое значение `API_URL`.

3. Попробуйте открыть список заявок в приложении. Посмотрите логи `web`.
4. Объясните, почему возникла ошибка и как она связана с указанным портом.
5. Исправьте порт в `API_URL`: верните `8000` вместо `9999`.
6. Снова примените настройки:

    ```bash
    docker compose -f compose.student.yaml up -d web
    ```

7. Проверьте, что список заявок снова открывается, и отправьте новую заявку.

**Что сдать:** исправленный `compose.student.yaml` и отчёт `evidence/K2-05.md`. Опишите, что перестало работать, приведите сообщение из логов, объясните причину и подтвердите успешную отправку заявки после исправления.

**За что начисляются баллы:**

- Показано, как проявляется ошибка — 1 балл.
- Объяснена связь ошибки с неверным портом — 1 балл.
- Настройки исправлены, заявка успешно отправлена — 1 балл.

**Вопрос для защиты:** какой порт должен использовать `web` для обращения к `api` внутри сети Compose: `8080` или `8000`? Почему?
