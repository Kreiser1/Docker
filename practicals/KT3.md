# КТ 3. Практические работы — 25 баллов

[Теория](../theory/KT3.md) · [Правила сдачи](../docs/SUBMISSION.md) · [Курс](../README.md)

Все команды выполняйте из корня своей копии, если явно не указано «внутри контейнера». Для КТ 2–4 нужны результаты предыдущих этапов. Рабочую копию Compose переключаем явно через `-f`; это тот же проект и те же тома, не два параллельных стенда.

## K3-01. CI/CD и ветки — 3 баллов

**Задача.** Опишите для своего проекта: событие запуска проверок, автоматический тест, сборку, решение о выпуске. Нарисуйте ветка → PR → main. Сравните с Git-flow и объясните, почему для короткой работы выбрана простая схема.

**Сдать:** файлы изменений, `evidence/K3-01.md` с командами, наблюдениями и выводом; для CI — ссылки на прогоны, для панели — JSON. Если работа устная/схематическая, достаточно схемы и ответа в отчёте.

**Критерии:** Различия CI/delivery/deployment — 1; схема веток — 1; обоснование выбора — 1.

**Проверка понимания:** Является ли сборка образа автоматическим deployment?

## K3-02. Первый workflow — 7 баллов

**Задача.** Скопируйте templates/student-ci.yml.example в .github/workflows/student-ci.yml. В своей копии включите Actions, если они отключены. Сделайте commit и push либо браузерный commit. Откройте именно Student CI, дождитесь результата. Найдите событие, SHA, runner, checkout, Python и вывод python --version.

**Сдать:** файлы изменений, `evidence/K3-02.md` с командами, наблюдениями и выводом; для CI — ссылки на прогоны, для панели — JSON. Если работа устная/схематическая, достаточно схемы и ответа в отчёте.

**Критерии:** Правильный путь YAML — 1; события push/PR — 1; runner и job — 1; checkout — 1; Python — 1; успешный запуск с SHA — 1; объяснение job/step — 1.

**Проверка понимания:** Почему зелёный python --version ещё не подтверждает работу приложения?

## K3-03. Тестовый барьер — 6 баллов

**Задача.** Добавьте после setup-python шаг run: python -m unittest discover -s tests -p test_app.py -v. Получите зелёный запуск. В test_create_request временно замените ожидаемый статус 201 на 200, закоммитьте и получите failed. Верните 201 и получите успешный запуск. Сохраните ссылки на оба SHA и существенные строки логов. Не добавляйте continue-on-error.

**Сдать:** файлы изменений, `evidence/K3-03.md` с командами, наблюдениями и выводом; для CI — ссылки на прогоны, для панели — JSON. Если работа устная/схематическая, достаточно схемы и ответа в отчёте.

**Критерии:** Реальный запуск тестов — 1; проверяемый контракт объяснён — 1; failed run — 1; причина assert — 1; исправленный run — 1; обе версии связаны с SHA — 1.

**Проверка понимания:** Почему неверное ожидание теста тоже делает CI красным?

## K3-04. Сборка после тестов — 6 баллов

**Задача.** В Student CI добавьте job build с runs-on: ubuntu-latest и needs: test. Добавьте checkout с тем же SHA Action, что в шаблоне. Команда сборки: docker build -f lab/Dockerfile -t devops-student:${{ github.sha }} lab. Повторите эксперимент ошибочного теста: build должен быть skipped. Восстановите тест, убедитесь, что test и build успешны.

**Сдать:** файлы изменений, `evidence/K3-04.md` с командами, наблюдениями и выводом; для CI — ссылки на прогоны, для панели — JSON. Если работа устная/схематическая, достаточно схемы и ответа в отчёте.

**Критерии:** Отдельный build job — 1; needs: test — 1; checkout — 1; реальная сборка — 1; тег SHA — 1; failed test действительно блокирует build — 1.

**Проверка понимания:** Где останется образ после удаления runner, если его не отправить в registry?

## K3-05. Разбор лога pipeline — 3 баллов

**Задача.** В своей ветке временно измените путь -f lab/Dockerfile на -f lab/MissingDockerfile. Получите ошибку build. Найдите первый полезный текст ошибки, объясните причину, исправьте путь и повторите запуск. Не меняйте тесты и не скрывайте код выхода.

**Сдать:** файлы изменений, `evidence/K3-05.md` с командами, наблюдениями и выводом; для CI — ссылки на прогоны, для панели — JSON. Если работа устная/схематическая, достаточно схемы и ответа в отчёте.

**Критерии:** Конкретная строка лога — 1; верный диагноз — 1; исправленный успешный запуск — 1.

**Проверка понимания:** Чем отсутствие Dockerfile отличается от ошибки теста?

После выполнения проверьте файлы в PR и передайте ссылку преподавателю. При ошибке приложите фактический вывод, а не предполагаемый успешный результат.
