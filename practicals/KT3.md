# КТ 3. Практические работы — 25 баллов

[Теория](../theory/KT3.md) · [Правила сдачи](../docs/SUBMISSION.md) · [Курс](../README.md)

Все команды выполняйте из корня своей копии репозитория. Для КТ 3 используйте приложение и Dockerfile, подготовленные на предыдущем этапе. Работы выполняются **по порядку**: сначала модель CI/CD, затем первый workflow, тестовый барьер, сборка после теста и разбор ошибки. Сохраняйте ссылки на собственные запуски `Student CI`, событие и SHA каждого run. Готовый `Course checks` не заменяет вашу работу.

## K3-01. CI/CD и ветки — 3 балла

**Задача.** Опишите для своего проекта событие запуска проверок, автоматический тест, сборку и отдельное решение о выпуске. Нарисуйте путь «короткая ветка → PR в `main` своей копии → проверка → слияние». Сравните этот маршрут с Git-flow и объясните, почему для небольшой учебной работы выбрана простая схема. Назовите, на каком этапе появится обратная связь об ошибке.

**Сдать:** `evidence/K3-01.md` со схемой и коротким объяснением. Реальный Actions run на этом шаге ещё не требуется.

**Критерии:** Различия CI/delivery/deployment — 1; схема веток и место проверки — 1; обоснование выбора — 1.

**Проверка понимания:** Является ли сборка образа автоматическим deployment?

## K3-02. Первый workflow — 7 баллов

**Задача.** Скопируйте `templates/student-ci.yml.example` в `.github/workflows/student-ci.yml`. Проверьте, что Actions разрешены в вашей копии; если они отключены и у вас есть доступ к настройке, включите их, иначе сообщите преподавателю. Сделайте commit и push либо браузерный commit. Откройте именно `Student CI`, дождитесь результата и найдите событие, SHA run, runner, шаги checkout и setup-python, вывод `python --version`. Шаблон настроен на `push` и `pull_request`; фактическое событие определяйте по выбранному run.

**Сдать:** файл workflow и `evidence/K3-02.md` со ссылкой на собственный run `Student CI`, его событием и SHA, найденными шагами и кратким объяснением их роли. Если Actions недоступны, сохраните файл и укажите фактическую причину; запуск нужно будет подтвердить после восстановления доступа.

**Критерии:** Правильный путь YAML — 1; настроенные события push/PR и событие выбранного run — 1; runner и job — 1; checkout — 1; Python — 1; успешный запуск с SHA — 1; объяснение job/step — 1.

**Проверка понимания:** Почему зелёный python --version ещё не подтверждает работу приложения?

## K3-03. Тестовый барьер — 6 баллов

**Задача.** После `setup-python` добавьте отдельный шаг `run: python -m unittest discover -s tests -p test_app.py -v`. Получите успешный run с реальными тестами. В `tests/test_app.py`, в тесте `test_create_request`, временно замените **ожидаемый** HTTP-статус `201` на `200`, сделайте commit и получите `failed` run. Верните ожидание `201`, сделайте новый commit и получите успешный run. Сохраните ссылки на неуспешный и исправленный запуски, их SHA и существенные строки логов. Не добавляйте `continue-on-error` и не скрывайте код выхода команды.

**Сдать:** обновлённый workflow и `evidence/K3-03.md` со ссылками на `failed` и исправленный успешный run, SHA каждого, строкой ошибки теста и объяснением причины. В итоговой версии тест снова ожидает `201`.

**Критерии:** Реальный запуск тестов — 1; проверяемый контракт объяснён — 1; failed run — 1; причина assertion — 1; исправленный run — 1; оба результата связаны с соответствующими SHA — 1.

**Проверка понимания:** Почему неверное ожидание теста тоже делает CI красным?

## K3-04. Сборка после тестов — 6 баллов

**Задача.** В `Student CI` добавьте отдельный job `build` с `runs-on: ubuntu-latest` и `needs: test`. Добавьте checkout с тем же SHA Action, что в шаблоне. Команда сборки: `docker build -f lab/Dockerfile -t devops-student:${{ github.sha }} lab`. Повторите эксперимент с ошибочным ожиданием теста из K3-03 **уже после добавления build**: при `failed test` зависимый `build` должен стать `skipped`. Восстановите тест, сделайте новый commit и убедитесь, что `test` и `build` успешны в одном run. `${{ github.sha }}` обозначает SHA, обрабатываемый этим run; для PR это может быть SHA проверяемого результата слияния.

**Сдать:** обновлённый workflow и `evidence/K3-04.md` со ссылками на run с `failed test`/`skipped build` и на исправленный успешный run, их событиями и SHA, строкой сборки и объяснением зависимости.

**Критерии:** Отдельный build job — 1; `needs: test` — 1; checkout в build — 1; реальная сборка — 1; тег с SHA run — 1; failed test действительно пропускает build — 1.

**Проверка понимания:** Где останется образ после удаления runner, если его не отправить в registry?

## K3-05. Разбор лога pipeline — 3 балла

**Задача.** В своей ветке временно измените путь `-f lab/Dockerfile` на `-f lab/MissingDockerfile`. Получите `failed build` при успешном `test`. Найдите первое содержательное сообщение об отсутствующем Dockerfile, объясните причину, исправьте путь и повторите запуск. Не меняйте тесты и не скрывайте код выхода команды.

**Сдать:** исправленный workflow и `evidence/K3-05.md` со ссылками на ошибочный и исправленный запуски, SHA каждого, существенной строкой лога, диагнозом и проверкой исправления.

**Критерии:** Конкретная строка лога — 1; верный диагноз — 1; исправленный успешный запуск — 1.

**Проверка понимания:** Чем отсутствие Dockerfile отличается от ошибки теста?

После выполнения проверьте итоговые файлы в PR **своей копии** и передайте ссылку преподавателю. В итоговом workflow должны остаться работающий тест и правильный путь к Dockerfile. В отчётах сохраните фактические ссылки на ошибочные и исправленные runs; не заменяйте их предполагаемым успешным результатом.
