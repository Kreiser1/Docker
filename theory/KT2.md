# КТ 2. Docker — необходимый минимум

[Работы КТ 2](../practicals/KT2.md) · [Курс](../README.md)

## 1. Образ и контейнер

Образ — упакованные файлы приложения, среда запуска и настройки по умолчанию. Контейнер — запущенный экземпляр образа со своими процессами и изменяемым слоем. Из одного образа можно запустить несколько контейнеров. Остановка контейнера не удаляет образ.

В нашем стенде web и api используют один образ, но переменная `ROLE` выбирает роль. Это учебное упрощение; в реальных системах компоненты часто собирают раздельно.

Команда `docker build` создаёт образ; `docker run` создаёт и запускает контейнер. `docker image inspect` показывает свойства образа, `docker ps` — запущенные контейнеры. Compose управляет набором контейнеров по конфигурации.

## 2. Dockerfile

Dockerfile — рецепт сборки. Минимальные инструкции:

| Инструкция | Смысл |
|---|---|
| `FROM` | Базовая среда, например Python |
| `WORKDIR` | Текущий каталог следующих действий |
| `COPY` | Перенос файлов из контекста сборки |
| `RUN` | Команда во время сборки |
| `ENV` | Переменные окружения по умолчанию |
| `USER` | Пользователь процесса контейнера |
| `EXPOSE` | Документирование внутреннего порта |
| `CMD` | Команда запуска контейнера |
| `LABEL` | Метаданные образа |

`RUN` и `CMD` выполняются на разных этапах. `EXPOSE 8000` не открывает порт на компьютере: публикация делается `-p` или `ports` в Compose.

В команде ниже файл рецепта — `lab/Dockerfile`, а **контекст** — каталог `lab`:

```text
docker build -f lab/Dockerfile -t devops-student:v1 lab
```

Поэтому `COPY app.py .` ищет `lab/app.py`, а не файл рядом с текущим терминалом. `.dockerignore` исключает ненужные файлы из контекста. Токены и базы в образ не копируют. Если поменяли код, скопированный через COPY, нужно пересобрать образ; прежний контейнер сам не обновится.

Образ состоит из слоёв. Неизменённые шаги сборки могут использовать кэш. Для простого проекта важно хотя бы не добавлять весь компьютер в контекст и не выполнять лишние установки при каждом запуске.

## 3. Порты, сеть и данные

`127.0.0.1:8080:8000` означает: принимать обращения только с этого компьютера на 8080 и передавать внутрь контейнера на 8000. Приложение внутри слушает `0.0.0.0:8000`, чтобы сеть контейнера могла к нему обратиться.

В сети Compose web обращается к `http://api:8000`. Имена сервисов заменяют знание изменяющихся IP. Порт 8080 нужен браузеру, но не соседнему сервису.

Изменяемый слой контейнера не подходит для долгого хранения заявок: при пересоздании он заменяется. **Named volume** хранит данные отдельно. Наш том `requests` подключён к `/data`. При пересоздании API идентификатор контейнера меняется, заявки остаются. Удаление тома уничтожит данные — для задания оно не требуется.

## 4. Compose

В YAML раздел `services` описывает сервисы; `image` выбирает образ, `environment` — параметры, `ports` — доступ с ПК, `volumes` — данные. Отступы определяют структуру; используйте пробелы, не табуляцию.

`docker compose config` проверяет и разворачивает конфигурацию. `up -d` запускает её в фоне, `ps` показывает состояние, `logs` — события, `stop` останавливает без удаления.

`depends_on` с `condition: service_healthy` задерживает старт web до успешной проверки api. Это не гарантирует, что api никогда не упадёт после старта, и не заменяет обработку ошибок в приложении.

## 5. Registry, tag и digest

Registry хранит образы. `tag` — удобное имя версии, которое может быть переназначено; `digest` — идентификатор конкретного содержимого. Commit SHA относится к исходникам, digest — к образу: это разные сущности.

В учебной работе используется локальный registry на `localhost:5000`. Он не требует внешней учётной записи и существует только на учебном ПК. `docker tag` добавляет имя существующему образу, `docker push` отправляет его в registry, `docker pull` получает обратно. Это не развёртывание приложения: после pull контейнер ещё нужно запустить.

Локальный HTTP-registry — изолированное учебное упрощение. Для внешнего реестра нужны аутентификация и защищённое соединение; отключать защиту кабинета не требуется.
