# КТ 1. Основы DevOps и Linux — необходимый минимум

[Работы КТ 1](../practicals/KT1.md) · [Курс](../README.md)

## 1. Что мы пытаемся улучшить

Представьте, что разработчик изменил форму заявки. На его компьютере всё работает, но в кабинете после обновления заявки перестали сохраняться. Сам по себе готовый код ещё не является работающим сервисом. Нужна цепочка: изменение → проверка → сборка → запуск → наблюдение → исправление.

DevOps — подход к совместной работе над этой цепочкой. Разработчик, тестировщик и специалист по эксплуатации разделяют ответственность за результат для пользователя. Автоматизация уменьшает число ручных действий; обратная связь помогает быстро заметить ошибку; небольшие изменения проще проверить и восстановить. Docker и GitHub — инструменты этого подхода, а не его определение.

В нашей «Мастерской» результат пользователя — получить номер принятой заявки. Красивая страница и сообщение «контейнер запущен» сами по себе этого не доказывают.

## 2. Как проходит запрос

```text
браузер → порт 8080 компьютера → web:8000 → api:8000 → SQLite в томе requests
```

`web` отдаёт HTML и передаёт запросы API. `api` проверяет данные и сохраняет заявку. SQLite — готовая часть приложения; самостоятельно изучать СУБД для КТ не требуется.

**Процесс** — запущенная программа. **Порт** — номер сетевой точки, которую процесс слушает. **Имя сервиса** в сети Compose разрешается во внутренний адрес. **HTTP** задаёт запрос и ответ; статус 200 обычно означает успех чтения, 201 — создание, 400 — неверный запрос, 404 — неизвестный путь, 503 — временную недоступность сервиса.

Числа 8080 и 8000 не обязаны совпадать: первое — вход с компьютера, второе — порт внутри контейнера. Адрес `localhost` всегда относится к тому месту, откуда выполняется обращение: в браузере это ПК, внутри web — сам web. Он не означает «любой соседний сервис».

## 3. Минимум Linux

Linux-команды ниже выполняются **внутри диагностического контейнера**, а не в PowerShell. Открыть его из корня курса:

```text
docker compose run --rm tools sh
```

Этот учебный контейнер разделяет пространство процессов и сеть **только с api данного проекта**. Поэтому можно увидеть API через `ps` и `ss`, не меняя систему компьютера.

```sh
pwd
ls
ps -ef
ss -lnt
curl -i http://127.0.0.1:8000/health
exit
```

`pwd` показывает текущий каталог, `ls` — его содержимое, `ps -ef` — процессы, `ss -lnt` — слушающие TCP-порты, `curl -i` — HTTP-ответ с заголовками. В `ps` ищите `python app.py`, в `ss` — порт 8000. `exit` возвращает в терминал компьютера.

Логи контейнера читаются с компьютера:

```text
docker compose logs --tail=20 api
docker compose logs --tail=20 web
```

Лог — запись о конкретном событии. В нашем приложении записи содержат время, роль и событие. `upstream_unavailable` у web сообщает, что web не смог обратиться к API. Это основание проверить зависимость, а не доказательство, что «сломалось всё».

## 4. Диагностика вместо случайных действий

Порядок работы: симптом → проверяемая гипотеза → одна проверка → вывод → исправление → повторный пользовательский сценарий. Например: «Страница открылась, список не загрузился. Возможно, API остановлен. Проверю статус api и лог web».

Меняйте по одной причине. Если одновременно пересобрать образ, переписать порт и удалить данные, уже нельзя понять, что исправило ошибку.

`/health` здесь проверяет только живой процесс. При остановленном API у web `/health` остаётся 200, а `/api/requests` возвращает 503. Поэтому нужно различать «процесс жив» и «операция пользователя выполняется».

## 5. GitHub как доказательство изменения

Репозиторий хранит файлы и историю. Commit фиксирует состояние и имеет SHA. Ветка позволяет работать отдельно; pull request показывает изменения и обсуждение. Проверяющий должен видеть, **какую версию** вы запускали и объясняете. Подробные действия: [сдача](../docs/SUBMISSION.md).
