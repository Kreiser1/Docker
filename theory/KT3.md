# КТ 3. CI/CD — необходимый минимум

[Работы КТ 3](../practicals/KT3.md) · [Курс](../README.md)

## 1. Что именно автоматизируем

В сервисе «Мастерская» страница может открываться, хотя API уже не сохраняет заявки. После изменения важно быстро проверить именно поведение сервиса. **Continuous Integration (CI)** — частое объединение небольших изменений с автоматическими проверками и быстрой обратной связью. **Continuous Delivery** — организация проверок и сборки так, чтобы изменение можно было выпустить управляемым решением. **Continuous Deployment** — автоматическое развёртывание каждого изменения, прошедшего установленные условия.

В этой КТ автоматизируем тестирование и сборку Docker-образа: `изменение → тест → сборка`. Это учебная часть цепочки доставки. Student CI не публикует образ и не развёртывает его в рабочей среде. Успешная сборка ещё не означает, что пользователь получил новую версию.

## 2. Ветки и короткая обратная связь

Для работы используем небольшую ветку → PR в `main` **своей копии** → проверку → слияние. Так проще сопоставить изменение с результатом. Git-flow добавляет долгоживущие `develop`/`release`-ветки и ветки исправлений; для некоторых моделей релизов это полезно, но переходов между ветками становится больше. В K3-01 нужно сравнить подходы и обосновать учебный выбор, а не выполнить Git-flow на практике. Для любой схемы важны вопросы: когда изменение встречается с общим кодом и когда автор узнаёт об ошибке?

## 3. Устройство GitHub Actions

Workflow — YAML-файл в `.github/workflows/`. В [шаблоне Student CI](../templates/student-ci.yml.example) его запускают события `push` и `pull_request`. Одно изменение может дать два отдельных запуска: после push в ветку и после создания или обновления PR. **Job** выполняется в среде runner; внутри job есть последовательность **steps**. Шаг `uses` подключает Action, `run` выполняет команду.

`checkout` получает исходники проверяемой ревизии. `setup-python` выбирает версию Python на runner. `python --version` показывает только версию и **не запускает тесты приложения**. Поэтому зелёный запуск исходного шаблона ещё не подтверждает сохранение заявок.

```text
push или pull_request → Student CI
  → job test: checkout → setup-python → позже тесты
  → job build: отдельный checkout → сборка образа
                  ↑ только после успешного test
```

Это схема для объяснения, **не YAML для копирования**. Jobs без зависимости могут выполняться параллельно: положение `build` ниже `test` в файле не создаёт барьер. `needs: test` означает, что сборка выполняется после успешного теста; при failed test зависимый build получает `skipped`. У каждого job собственная среда runner, поэтому build снова получает исходники через checkout.

**Тонкость с SHA.** При `push` проверяется отправленный commit. При `pull_request` GitHub по умолчанию проверяет результат предполагаемого слияния с базовой веткой; SHA этого run может отличаться от последнего SHA ветки PR. В отчёте указывайте событие, ссылку на run и SHA, показанный в нём.

## 4. Как тест становится барьером

Тест задаёт условия, выполняет действие и сравнивает фактический результат с ожидаемым. В `tests/test_app.py` тест `test_create_request` отправляет заявку и проверяет HTTP `201` и сохранение записи. Тесты запускают учебные процессы web и API и обращаются к ним по HTTP; они не проверяют Docker-контейнеры или развёртывание. При несоответствии команда тестирования завершается с ошибкой, а Actions отмечает шаг как `failed`.

Команда тестирования проекта:

```text
python -m unittest discover -s tests -p test_app.py -v
```

В логе должны быть названия тестов, число проверок и `OK` либо описание ошибки. Для доказательства барьера нужны два запуска: намеренно ошибочная версия и исправленная. Не используйте `continue-on-error` и `|| true` для скрытия падений.

В K3-03 временно меняется **ожидание в тесте**, а не поведение приложения: `201` на `200`. Красный run показывает работу барьера, но причина отказа здесь — намеренно неверное ожидание. После возвращения `201` нужен новый успешный run. Зелёный тест подтверждает только выполненные проверки на указанной ревизии, а не все возможные требования.

## 5. Образ и происхождение

В K3-04 job `build` собирает образ только после успешного `test` **в том же запуске workflow**. Тег вида `devops-student:<SHA>` связывает имя образа с SHA, который обрабатывал run; при PR это может быть SHA проверяемого результата слияния. Git commit SHA определяет ревизию исходников, Docker tag — изменяемое имя образа, а digest — конкретное содержимое образа. Сборка на временном runner не отправляет образ в registry и не делает его доступным после завершения runner. Для этой КТ достаточно подтверждённой сборки и работающего барьера; публикация и развёртывание не добавляются к требованиям на баллы.

## 6. Разбор ошибок и доступ

Сначала установите событие и SHA run, затем найдите первый job со статусом `failed`, внутри него — первый упавший step и содержательное сообщение. `skipped` у build после failed test — ожидаемое действие барьера, а не ошибка сборки. Ошибка утверждения теста и отсутствие Dockerfile требуют разных исправлений. Исправьте одну причину и повторите проверку в новом run.

В учебном workflow достаточно `permissions: contents: read`; внешние секреты не нужны. Полный SHA у `uses` закрепляет конкретный код Action, но сам по себе **не доказывает**, что этот код проверен и безопасен. Не вставляйте секреты в YAML или лог и не расширяйте права токена ради зелёного статуса. Меняющиеся детали сверяйте с [GitHub Workflow syntax](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax), [Events](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows) и [Secure use](https://docs.github.com/en/actions/reference/security/secure-use).
