# КТ 3. CI/CD — необходимый минимум

[Работы КТ 3](../practicals/KT3.md) · [Курс](../README.md)

## 1. Что именно автоматизируем

После каждого изменения нужно проверить, что приложение запускается и сохраняет заявку. Если выполнять всё вручную, шаги пропускаются. **Continuous Integration (CI)** — регулярное объединение небольших изменений с автоматическими проверками. **Continuous Delivery** — готовность проверенного изменения к выпуску по решению человека. **Continuous Deployment** — автоматическое развёртывание после прохождения условий.

В этой КТ автоматизируем тестирование и сборку Docker-образа. Это учебная часть цепочки доставки. Автоматического production-деплоя здесь нет; нельзя называть сборку образа полным развёртыванием.

## 2. Ветки и короткая обратная связь

Для работы используем короткую ветку → PR → проверку → main. Так проще сопоставить изменение с результатом. Git-flow добавляет долгоживущие develop/release/hotfix-ветки и может быть полезен для отдельных моделей релизов, но увеличивает число действий. Он не является обязательным способом работать с CI/CD. Нам достаточно простой схемы и небольших изменений.

## 3. Устройство GitHub Actions

Workflow — YAML-файл в `.github/workflows/`. Событие `push` или `pull_request` запускает workflow. **Job** выполняется на runner — отдельной машине; внутри job есть последовательность **steps**. Шаг `uses` подключает Action, `run` выполняет команду.

`checkout` получает файлы текущего изменения. `setup-python` выбирает версию Python на runner. `python --version` показывает только версию и **не запускает тесты**.

```yaml
permissions:
  contents: read
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      # checkout, setup-python и команда тестов
  build:
    needs: test
    runs-on: ubuntu-latest
    steps:
      # новый checkout и сборка
```

У разных jobs разные рабочие окружения. Поэтому build тоже должен получить файлы. `needs: test` означает, что сборка выполняется после успешного test. Если тест падает, build должен быть пропущен. Простое расположение jobs сверху вниз зависимости не создаёт.

## 4. Как тест становится барьером

Тест задаёт ожидаемое поведение, выполняет действие и сравнивает фактический результат. Например, корректная заявка должна вернуть HTTP 201 и сохраниться. При несоответствии команда тестирования завершается ненулевым кодом; Actions отмечает шаг как failed.

Команда тестирования проекта:

```text
python -m unittest discover -s tests -p test_app.py -v
```

В логе должны быть названия тестов, число проверок и `OK` либо описание ошибки. Для доказательства барьера нужны два запуска: намеренно ошибочная версия и исправленная. Не используйте `continue-on-error` и `|| true` для скрытия падений.

В нашем тесте `test_create_request` проверяет статус 201. В учебном эксперименте временно меняется ожидаемое значение на 200, чтобы увидеть отказ проверки; затем восстанавливается правильный контракт 201. Это проверка механизма CI, а не новое требование к приложению.

## 5. Образ и происхождение

Собирайте образ из того же SHA, который прошёл тесты. Тег вида `devops-student:<SHA>` связывает результат с исходниками. Сборка внутри runner не отправляет образ в registry и не сохраняет его навсегда: runner завершит работу. Для этой КТ достаточно подтверждённой сборки; публикация и развёртывание — самостоятельные дальнейшие этапы, а не скрытое требование на дополнительные баллы.

## 6. Разбор ошибок и доступ

Сначала найдите первый упавший шаг и конкретное сообщение. Ошибка assert, отсутствие файла и недоступный registry — разные причины. Исправьте одну причину и повторите проверку на новом SHA.

В учебном workflow достаточно `contents: read`; внешние токены не нужны. Длинный SHA у `uses` фиксирует проверенную версию Action. Не вставляйте секрет в YAML и не запускайте чужой код в привилегированном контексте ради зелёного статуса.
